# Papuma — Storage-neutral Specification

Status: **draft 0.1** (2026-10-16) · first slice of phase 1 of the
[interop and hardening roadmap](../analyses/interop-and-hardening-roadmap.md)

The kernel exists twice (PostgreSQL and SQLite) and may exist a third time (Rust).
What lets two implementations call themselves *compatible* is not shared code but
a shared **specification** and a shared **conformance suite**. This folder holds
both. It describes the *logical* contract; the PostgreSQL tables and the snapshot
cursor of [feed-wire-format.md](../feed-wire-format.md) are one realisation of it.

| Part | Status |

| [patch.md](patch.md) — patch operations (`set`, `remove`, `increment`) and the divergences it found between the two kernels (fixed) | draft |

chapter, the event log.

## Conformance

An implementation conforms to this draft when it passes every case in
[vectors/](vectors/). Each vector file is one JSON object:

```jsonc
{ "spec": "papuma-changes", "version": "0.1", "kind": "diff", "cases": [ { "name": "...", /* ... */ } ] }
```

- `diff.json` — `Diff(before, after)` must produce `diff` (wire format). `before`
  or `after` is `null` for insert or delete. A case with `error` must be rejected.
  Every non-error case must also be reversible (see [changes.md](changes.md#reversibility)).
- `patch.json` — applying `ops` in order to `before` must yield `after` or fail with
  `error`. Both engines pass every case (history: [patch.md](patch.md#3-history-divergences-found-and-fixed)).
  Runners: `PatchVectorInProcessTests` (the in-process definition, `Papuma.Kernel.Core.Tests`,
  no database) and `PatchVectorPostgresTests` (the real PostgreSQL expression).
- `canonical.json` — `canonical(parse(inputJson))` must equal `canonical`, or fail with `error`
  ([canonical-json.md](canonical-json.md)). `inputJson` is raw text because the number text matters.
- `hash.json` — key derivation, v2 hashes and the key-check value for a fixed test master key
  ([canonical-json.md](canonical-json.md#2-the-v2-hash)). Generated by `reference/canonical_hash.py`.
- `policy.json` — applying `policies` to `diff` for the given document type and id
  must produce `expected`. Policies not listed default to `Track`. A case with `hashKey` runs under
  the keyed v2 hash; a `Hash` policy that applies without a key must fail (`"error": "no-hash-key"`,
  see [changes.md](changes.md#the-hash-policy-is-keyed-v1-is-read-only)).

Comparison is **JSON-semantic** (object key order is irrelevant), except where a
case lists `orderedPaths`, which pins the emission order of diff entries.

The reference runners live in
[`Papuma.Kernel.Core.Tests`](https://github.com/papumabiz/Papuma.Kernel/tree/master/tests/Papuma.Kernel.Core.Tests/Spec):
they run the vectors against `Papuma.Kernel.Core`, which both the PostgreSQL and the
SQLite kernel share, in milliseconds and without a database. The patch vectors also run
against the real PostgreSQL expression. End-to-end vectors through a full session on each
engine are a later slice.

## Beyond the vectors

Vectors pin what we thought of. Two further kinds of test check what we did not, and any implementation
of this specification should have the same:

- **Properties over generated documents** (`EngineRobustnessTests`, seeded and reproducible by seed): for thousands
  of random documents whose keys contain dots, backslashes and unicode, whose numbers are spelled many ways, and
  which are mutated at random — applying a diff forward and backward restores the documents, the wire form
  round-trips, paths are well formed and ordered, equal documents give an empty diff, canonical JSON is stable under
  key order, number spelling and re-parsing, **the diff and the canonical form agree on whether two numbers are
  equal**, and no policy lets a protected value through.
- **A differential test of the two patch implementations** (`PatchDifferentialTests`, against a real PostgreSQL): the
  same random documents and operation lists must succeed or fail together and leave the same document. It found a
  real divergence the hand-written vectors missed (a removal below an array).

- **Random operation sequences against real sessions** (`SessionModelTests`, `SqliteSessionModelTests`; one shared
  `SessionModelRunner`): save, patch, delete, roll back and load, grouped into sessions that commit or are abandoned,
  with right and wrong expected versions, run against a real engine and an in-memory reference model at once. State,
  version numbers, concurrency and not-found errors, abandoned sessions and the complete change history — including
  field policies — must match the model, and a history of values must replay to every state it passed through. The
  first run found a policy bypass (`[JsonIgnore(Condition = WhenWritingNull)]` switched the property's policy off).

Structural limit: a document nests at most 64 levels of objects and arrays — the limit of the serializer and
parser, so the engines accept exactly what the stores can write and read; deeper input is refused with a clean error.

## Changing the vectors

Vectors are **hand-reviewed**, not generated on every run: a failing vector is
either a kernel regression or a deliberate spec change. In the second case change
the vector, bump `version` in the vector file, and note it in
[changes.md](changes.md). Never edit a vector just to make a test pass.
